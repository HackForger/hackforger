# 黑客故事

> 涵盖参与者/开发者操作

---

## 史诗 1: Hackathon（黑客松）生命周期

> **史诗假设:** 我们相信，提供一个 Git 原生的黑客松平台——参赛作品以 PR 形式提交、评审直接基于代码进行——将提高提交的完整性并减少组织者的运营负担，因为代码与提交之间的鸿沟被彻底消除。

---

### 故事 H-006: 注册参加 Hackathon

- **概要:** 黑客注册后自动获得组织成员资格以便访问 Git 仓库

#### 用例:
- **作为** hacker
- **我想要** 注册参加黑客松并选择赛道
- **以便** 我可以 Fork 赛道仓库并开始开发

#### 验收标准:

- **场景:** 黑客注册参加已开放的黑客松
- **假设:** 黑客松处于 `Open(1)` 状态
- **且假设:** 我以 `hacker1` 身份登录且尚未注册
- **当:** 我注册参加黑客松并选择 "DeFi Track"
- **那么:** 注册记录以 `Approved(1)` 状态创建，我被加入黑客松 Organization 成为成员，同时发出 `hackathon_registered(31)` Feed 事件

**旅程参考:** J1 Steps 1.8, 1.9

---

### 故事 H-007: 通过 Fork + PR 提交作品

- **概要:** 黑客通过从其 Fork 创建 PR 来提交作品——提交物就是 PR 本身

#### 用例:
- **作为** 已注册的 hacker
- **我想要** Fork 赛道仓库、开发项目，然后提交 PR 作为我的参赛作品
- **以便** 我的提交有时间戳、可对比差异、可审查——完整的 Git 历史作为工作量证明

#### 验收标准:

- **场景:** 黑客在 Hacking 阶段提交作品
- **假设:** 黑客松处于 `Hacking(2)` 状态
- **且假设:** 我已将 `web3-innovation/defi-track` Fork 到 `hacker1/defi-track`
- **且假设:** 我已向我的 Fork 推送了提交
- **当:** 我从 `hacker1:main` 向 `web3-innovation/defi-track:main` 创建 PR 并将其注册为黑客松提交
- **那么:** 提交记录与 PR 关联创建，发出 `hackathon_submitted(32)` Feed 事件，提交出现在黑客松排行榜上（未评分）

- **场景:** Hacking 阶段关闭后提交
- **假设:** 黑客松处于 `Judging(3)` 状态
- **当:** 我尝试创建提交
- **那么:** 请求被拒绝——提交已关闭

**旅程参考:** J1 Steps 1.11, 1.14, 1.15

## 史诗 3: Grant（资助）生命周期

> **史诗假设:** 我们相信，两阶段资助模型（Finalized = 承诺拨款, Distributed = 审核后释放资金）将提高资助的问责性，因为组织者可以在释放资金前验证项目进展。

---

### 故事 G-002: 提交 Grant 申请

- **概要:** 黑客提交项目提案以申请资金

#### 用例:
- **作为** 开发者
- **我想要** 提交项目提案，包含描述、申请金额和仓库链接
- **以便** 资助组织者可以评估我的项目是否值得资助

#### 验收标准:

- **场景:** 黑客提交资助申请
- **假设:** Grant Round #1 处于 `Open(1)` 状态
- **当:** 我提交项目 "DeFi Testing Framework"，申请 1000 Credits 并附上仓库链接
- **那么:** 项目以 `Pending` 状态创建，同时发出 `grant_project_submitted(40)` Feed 事件

- **场景:** 轮次关闭后提交
- **假设:** Grant Round #1 处于 `Review(2)` 状态
- **当:** 我尝试提交项目
- **那么:** 请求被拒绝——申请已关闭

**旅程参考:** J3 Steps 3.3, 3.4

## 史诗 4: Credits（积分）经济体系

> **史诗假设:** 我们相信，将黑客松奖金、悬赏奖励和资助资金统一到一个可兑换的内部 Credits 经济体系中，将提高平台参与度，因为参与者可以看到在所有活动中积累的切实价值。

---

### 故事 C-001: 查看余额和交易历史

- **概要:** 用户查看 Credits 余额并浏览所有交易记录

#### 用例:
- **作为** 平台参与者
- **我想要** 查看我的 Credits 余额以及所有充值、扣款和兑换的历史记录
- **以便** 追踪我在黑客松、悬赏和资助中的收入和支出

#### 验收标准:

- **场景:** 用户查看余额
- **假设:** 我以 `hacker1` 身份登录且有累积的 Credits
- **当:** 我查看 Credits 面板
- **那么:** 我看到当前余额 (1950) 和按时间倒序排列的交易列表，显示每笔充值来源（黑客松奖金、悬赏奖励、资助拨款）及所有扣款

**旅程参考:** J4 Steps 4.3, 4.4

---

### 故事 C-002: 兑换 Credits

- **概要:** 用户用 Credits 兑换市场中的奖励

#### 用例:
- **作为** 拥有累积 Credits 的参与者
- **我想要** 浏览可用奖励并用 Credits 兑换
- **以便** 为我的贡献获得切实的回报

#### 验收标准:

- **场景:** 成功兑换
- **假设:** 我有 1950 Credits，且存在 "GitHub Copilot - 1 Month" 选项，价格为 200
- **当:** 我兑换该选项
- **那么:** 200 Credits 被原子性扣除，创建 `RedeemOrder`（兑换订单）并处于 `pending` 状态，记录 `redeem` 交易，同时发出 `credits_redeemed(42)` Feed 事件

- **场景:** 余额不足
- **假设:** 我有 50 Credits
- **当:** 我尝试兑换价值 200 Credits 的选项
- **那么:** 请求被拒绝，提示余额不足

**旅程参考:** J4 Steps 4.5, 4.6
